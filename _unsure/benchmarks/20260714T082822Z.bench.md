## Gate 2 — establish the bottleneck

This is the first baseline so Gate 2 reads "establishes the cost
signature on the representative workload." Each of the four hot paths
is captured below with the numbers subsequent phases must improve.

| `scatter_sample` | 100 000 rows, 4 cols | **6.81 ms** |
| `scatter_sample` | 500 000 rows, 4 cols | **24.37 ms** |
| `scatter_sample` (continuous colour) | 200 000 rows, 4 cols | **14.42 ms** |
| `scatter_sample` (categorical colour) | 200 000 rows, 4 cols | **24.87 ms** |

These confirm the rough scaling the plan predicted:

- **Scatter sampler is O(n)** on the under-effective-limit path (10 000 →
  100 000 rows = 31× time, which matches the 10× row growth plus the
  linear per-row cost; 500 000 rows goes sub-linear because we drop
  into the bounded stride path).
- **Rolling bands is O(n × window × columns)** in the worst case. The
  200 000 / 2 000 case is 18× slower than 200 000 / 50 — **exactly
  what Phase 2 is meant to fix** with prefix sums.
- **Correlations matrix is O(n² × pair_cost)** at fixed row count.
  4 → 8 cols (2× pairs) costs 3.9×; 8 → 16 (4× pairs) costs 3.9×. The
  pair-loop dominates; Phase 3 will attack that.

Stage timings show the bottleneck signature the plan expected:

- **Scatter sampler is dominated by `sample_ns`** (14.8 ms / 19.2 ms ≈
  77 % of scatter CPU). The `sample` stage is the LTTB + stride loop —
  exactly the inner-loop Phase 1 is targeting.
- **Correlations pair_calc_ns (154 ms)** is huge because the warmup
  ran once at upload; `pair_calc_ns_total` measures cumulative CPU
  regardless of cache hit. The actual on-the-wire cost is dominated
  by cache hits (sub-millisecond JSON encode). The bottleneck Phase 3
  plans to attack is the **first miss** cost — visible only on cold
  uploads, not in steady state.
- **Rolling compute (21.5 ms)** for 60 rolling requests = **358 µs /
  request** at the stage level. The on-the-wire p95 of 964 ms is
  dominated by JSON serialisation + spawn_blocking overhead, not by
  the rolling arithmetic. Phase 2's prefix-sum refactor will tighten
  the inner loop but the request-level p95 will not collapse unless
  the spawning/serialisation overhead also drops — that's a separate
  optimisation target.

## Known measurement caveats

1. **Dirty working tree at capture time.** The captured env records
   uncommitted edits to `Cargo.toml`, `crates/edatime-core/src/metrics.rs`,
   `crates/edatime-service/Cargo.toml`, and several handler files. These
   are the Phase 0.1 telemetry changes that have already landed in
   `master` (per `git status`) — re-capturing against a clean tree is
   the next step.
2. **Rate limit was overridden** to 200 000 / 60 s. The default 1 000 /
   60 s is documented to be a "local analytics tool" guard, not a
   benchmark target; the override is justified in
   `scripts/benchmark.md`. Subsequent baselines must use the same
   override to be comparable.
3. **`scatter_correlations` numbers are cache-dominated** because the
   warmup fires once on upload and the matrix fits the 60-second
   TTL window. Subsequent baselines should explicitly age the cache
   (`curl /api/v1/scatter/correlations` at t=0 vs t=120) to get an
   honest cache-miss cost.
4. **WSL2 environment.** The Ryzen 9 9950X host is not bare metal;
   I/O and clock behaviour under WSL2 differs from a Linux server.
   Cross-host comparisons need to subtract the WSL overhead.

## Why superseded

The newer baseline [`20260714T150000Z.bench.md`](20260714T150000Z.bench.md)
captures the same workload on a later SHA (`86f41294`, post-cleaning-plans)
using a corrected procedure:

- `scripts/bench_http.mjs` now waits `--rundown 15` after the run
  loop ends, so the `cpu_admission` snapshot reflects
  `submitted == started == completed` rather than a mid-flight
  imbalance.
- RSS sampling actually fires now (the previous `rssCandidates.find`
  predicate matched `args.pid = null` and never fell through to
  `$EDATIME_PID`).
- `cpu_admission_pending` is reported as `{queued, running}` with a
  non-negative math fix.
- The `EDATIME_*` server-start env is captured in the `.env` artefact
  so a re-run on another host can use the same rate-limit override.

The pre-fix procedure has a *systematic* `submitted > started` artefact
on `query` and `analytics` (the spawn_blocking queue was backed up at
snapshot time). The numbers in this file are real measurements but
the queue-depth reading is misleading. The newer baseline is the one
to use for Phase 1+ gate decisions.
